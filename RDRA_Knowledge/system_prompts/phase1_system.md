## RDRAナレッジ
（元ファイル: RDRA_Knowledge/1_RDRA/RDRA.md）

```
# RDRA構造の説明
- 「アクター」：システムに関わる人の役割を表す
- 「アクター群」：同じような役割を持つ「アクター」をまとめ、組織の役割を示す場合もある
- 「外部システム」：システムと連携する外部のシステムを表す
- 「外部システム群」：同じような関係を持つ「外部システム」をまとめる
- 「コンテキスト」：システムを表すモデル「情報」「状態モデル」「条件」「バリエーション」をまとめる
- 「情報」：システムが扱うビジネス上の情報を表す ビジネス上管理されているID単位に存在する
- 「状態」：情報の変化を状態として扱い、ビジネス上管理する対象となる 状態を遷移させながらビジネスが進む
- 「業務」：最上位の会社の機能（マーケティング、販売や在庫管理...） BUCを構成要素に持つ
- 「BUC」：業務の価値を実現する単位で、業務フローの単位になる 同じ業務内でも関わるアクターや外部システムの違いでBUCが分かれる
- 「アクティビティ」：意味をもったまとまった一つの作業 仕事で関りのあるものを関連させる
- 「UC」：システムを使ってまとまった一つの意味をもつ作業 システムとの接点となり関りのあるものを関連させる
- 「画面」：アクターとシステムとのインターフェースになる
- 「イベント」：外部システムとのインターフェースになる
- 「タイマー」ビジネス上の時間的な区切りを表す　２５日締め　月末　

# モデル間のつながりの規則
- 「業務」は複数の「BUC」を配下にもつ
- 「BUC」は複数の「アクティビティ」を配下にもつ
- 「アクティビティ」(仕事)を行う「アクター」がつながる
- 「アクティビティ」(仕事)でシステムを使う場合は「UC」につながる
- 「UC」は情報を操作する
- 「アクター」は画面を使ってUCを操作する
- 「外部システム」は「イベント」で「UC」と連携する
- 「UC」が定時に活動する場合に「タイマー」につながる
- 「情報」は「情報」とつながることで構造化する
- 「状態モデル」は複数の「状態」を持つ
- 「UC」が「状態」を遷移させる
- 状態遷移は「状態モデル」内で「状態」を変える
- 「コンテキスト」は「情報」、「状態モデル」、「条件」、「バリエーション」を配下に複数持つ
- 「コンテキスト」内の構成要素は同一のIDで管理される
- 「条件」は「バリエーション」と「状態モデル」の組合せで出来ている
- オブジェクトは必ず対応するメタモデルが存在し、オブジェクトのつながりはメタモデル間のつながりの規則に従う

# 定義内容は各モデルのオブジェクトとして定義する
以下に例を示す
「会員」：モデルがアクター、オブジェクトが「会員」になる
「受注」：モデルが情報、オブジェクトが「受注」になる
「受注を登録する」：モデルがUC、オブジェクトが「受注を登録する」になる
```

## 初期要望
（元ファイル: 初期要望.txt）

```
### 背景
Spring ModulithとDDD（ドメイン駆動設計）を学習・実践するためのデモプロジェクト。
マイクロサービスアーキテクチャを採用し、事業領域ごとにモジュールを分離するシステム。

### アクター
・従業員（基本利用者）
・プロダクトオーナー（PO）
・スクラムマスター（SM）
・開発者
・トラッキング担当従業員
・システム管理者

### 外部システム
・OAuth2認可サーバー（authorizationモジュール）
・Amazon S3（帳票ストレージ）
・MinIO（開発用ストレージ）

### 要求
・Scrumプロジェクト管理を支援する
・電子帳票基盤を提供する
・各事業領域を独立したモジュールとして管理する

### 制約
・Spring Modulithによるモジュール境界の違反を検出する
・各事業領域は独立したデータベーススキーマを持つ
・OAuth 2.0 Authorization Code with PKCEフローを使用する
・アクセストークンの有効期間は15分以内とする

### ビジネスポリシー
・認証はシングルサインオンで統一する
・API Gatewayで認証・認可を一元管理する
・機微な情報は専用のデータベースに保管する
・JWTはRS256署名を使用する
・リフレッシュトークンの有効期間は7日以内とする

## ビジネスパラメータ
・事業領域の追加に簡単に対応できる
・モジュール間の依存関係を明示的に管理する

## ビジネス概要
・Agiloom（AG）：Scrumプロジェクト管理
- プロダクトディスカバリー：プロダクト目標・バックログの管理
- 要求バックログ管理：バックログ項目の作成・明確化・順序付け
- 優先順位決定：価値と優先順位の判断
- スプリント実行：スプリント計画・進捗管理
- 品質検証：完成の定義を満たす品質の確認
- 成果適応：インクリメントの評価と改善

・電子帳票（EF）：帳票基盤管理
- 帳票定義管理：帳票種類・レイアウト・テンプレートの管理
- 帳票生成：PDF・Excelなどの帳票ファイル生成
- 帳票管理：帳票情報・バージョン・状態の管理
- 帳票配信：利用者・組織・取引先への帳票配信
- 帳票閲覧・プレビュー：PDF・Office文書のプレビュー・印刷・ダウンロード
- 承認・確認：帳票の承認・差戻し・確認状況管理
- 帳票保管・廃棄管理：保存期間・廃棄候補・廃棄管理
- アーカイブ管理：S3ストレージクラス変更・移行・完全性検証

・ジョブ管理（JM）：ジョブ・権限管理
- ジョブ定義：ジョブの登録・管理
- ジョブ実行：ジョブの実行・監視
- 権限管理：権限の付与・剥奪

・関連付け（AS）：関連付け管理
- 人材管理：人材とプロジェクトの関連付け
- 関連付け管理：エンティティ間の関係管理

・承認申請（AR）：承認ワークフロー
- 承認リクエストの作成・追跡
- 承認フローの定義・実行

・通知（NT）：通知処理
- メール通知
- システム内通知
- Webhook通知

・レジストリ群：共通マスタ管理
- カレンダーレジストリ（CA）
- 税率レジストリ（TA）
- 住所レジストリ（AD）
- 元号レジストリ（ER）
- 金融機関レジストリ（FI）

・開発運用（DO）：開発・運用支援
- データベース定義管理
- Snowflake ID生成
```
